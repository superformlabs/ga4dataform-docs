GA4 Parameter Detection

💎Premium Feature

This feature is exclusive for Premium users!

The GA4 Parameter Detection module automatically discovers and tracks user properties, custom event parameters, and item parameters in your GA4 raw export. This powerful auditing tool helps you identify configuration gaps, data quality issues, and optimization opportunities in your GA4 implementation.

Key Features​

  • Automatic Discovery: Identifies parameters in your data that aren't configured
  • Configuration Validation: Flags configured data types that lose values, and type differences that do not
  • Issue Model: One row per issue with severity, evidence, active/resolved status and a suggested fix
  • Junk Value Detection: Flags placeholder values such as undefined, null or unresolved {{GTM variables}}
  • Expected Values: Checks values against your own rules (regex, allowed list, numeric range) and flags well-formed but wrong values
  • Coverage and Missing Days: Shows how many events carry a parameter, and on which days it went missing
  • Sample Value Analysis: Shows actual values being collected for each parameter
  • Trend Monitoring: Tracks parameter usage over time with daily granularity
  • Config Generation: Suggests configuration code for discovered parameters and type fixes for lossy ones
  • PII Detection: Scans parameter names, values and URL query strings for personally identifiable information
  • Suppressions and Assertions: Accept known findings, and get opt-in alerts when a new issue appears
  • Multi-Property Support: Tracks parameters per GA4 property with property_id and property_name columns
New in Premium v2.2.18

Expected values: rules for what a parameter's values should look like, with a new unexpected_values issue and an opt-in assertion. The missing_days assertion no longer raises false alerts right after an update. Existing installs: read Upgrading from earlier versions.

New in Premium v2.2.17

The module was overhauled: new issues and daily_health tables, an issue model with suppressions and opt-in assertions, junk value and missing-day detection, improved PII detection, and a slim custom config. Existing installs: read Upgrading from earlier versions.

Configuration​

The module uses a YAML configuration file: includes/custom/modules/ga4_parameter_detection/config.yaml

Your custom file only holds the keys you want to change. Every other option takes its default from includes/core/modules/ga4_parameter_detection/config.yaml - the full reference with every key and comment. Do not edit the core file: the installer overwrites it on update. Copy a key into your custom file to override it.

How your custom file is merged with the core defaults:

  • Single values (for example enabled or rate_threshold): your value wins.
  • Lists (for example exclude_params, known_pii_param_names, suppressions): your entries are appended to the core list.
  • Named entries in pii_value_patterns: your entry replaces the core entry with the same name. Copy the whole entry from the core file and change what you need - an entry without name, regex and enabled stops compilation with an error.

See How Configuration Works for the general rules.

Date Range Control​

max_lookback_days: 7
start_date: '9999-01-01'

When running a full refresh, the module automatically selects the more recent of two possible start dates to prevent accidentally processing excessive historical data:

  • max_lookback_days: Maximum days to look back from today
  • start_date: Earliest absolute date to process (set to 9999-01-01 by default so that any "real" date is intentionally set by the user)

This design allows you to set a distant start_date for comprehensive historical analysis when needed, while protecting against unintentionally querying years of data during rebuilds. The module will automatically limit processing to recent data based on the max_lookback_days setting, ensuring efficient rebuilds even after extended periods without updates.

BigQuery Cost Impact

These date settings determine how much raw GA4 data gets scanned - use shorter ranges to reduce processing costs. Querying the output parameter detection tables will be rather low cost as they are already aggregated.

Filtering​

Exclude Specific Parameters​

Skip tracking for known parameters you don't want to monitor.

BigQuery Cost Impact

Parameter filtering only affects what appears in the output tables - it doesn't reduce BigQuery processing costs since the module still scans all raw GA4 data within the configured date range.

exclude_params: ["debug_mode", "test_parameter"]

Exclude Parameter Categories​

Skip tracking for known categories you don't want to monitor. Useful if you are not interested in 'standard' parameters for example.

BigQuery Cost Impact

Parameter category filtering only affects what appears in the output tables - it doesn't reduce BigQuery processing costs since the module still scans all raw GA4 data within the configured date range.

exclude_category: ["standard"]

Filter by parameter type:

  • standard: Built-in GA4 parameters
  • custom: Parameters you've configured in includes/custom/modules/ga4/config.js
  • discovered: Parameters found in data but not configured

Event-Based Filtering​

Skip tracking for events you don't want to monitor.

BigQuery Cost Impact

Event filtering only affects what appears in the output tables - it doesn't reduce BigQuery processing costs (unless your raw GA4 tables are clustered by event_name!) since the module still scans all raw GA4 data within the configured date range.

# Skip parameters from certain events
exclude_events: ["session_start", "first_visit", "user_engagement"]

# OR focus on specific events only
include_events: ["purchase", "add_to_cart"]
Mutually Exclusive

Use either exclude_events OR include_events, not both simultaneously.

Sample Value Configuration​

These settings control how many example values to collect for each parameter. Samples are ranked by frequency, so you'll see the most commonly occurring values first.

sample_value_count_daily: 5
sample_value_count_agg: 50

Control how many sample values to collect:

  • sample_value_count_daily: Samples per parameter per day
  • sample_value_count_agg: Total samples across all dates. The aggregated table ranks values by their summed occurrences within the daily top samples

With pii_detection.mask_pii_in_samples: true, detected PII is replaced with [MASKED-<type>] in all sample values.

Multi-Property Support​

When you have multiple GA4 properties configured via EXTRA_GA4_DATASETS_ARRAY in the GA4 module, the Parameter Detection module automatically tracks parameters per property. All output tables include property_id and property_name columns, enabling per-property parameter auditing.

No additional configuration is needed - multi-property detection activates automatically when the GA4 module is set up with multiple properties.

Junk Value Detection​

Junk values are placeholders a tag sends when a variable is undefined, such as undefined, null, [object Object] or an unresolved GTM variable like {{Page Path}}. The module counts them per parameter, event and day (junk_occurrence_count). A row gets the junk_values issue when the junk share reaches rate_threshold and the parameter has at least min_occurrences occurrences that day.

junk_detection:
  rate_threshold: 0.05
  min_occurrences: 50

Standard item fields (item_id, item_name, item_category and so on) drop (not set) before detection, so it never counts as junk for them. Lists such as exact_values and regex_patterns are appended to the core defaults; set enabled: false to turn junk detection off.

Missing Days​

A parameter gets the missing_days issue for an event when it is absent on at least min_missing_days of the final days the event fired (counted from the first day the parameter was seen on that event), and that share reaches min_missing_share.

missing_days:
  min_missing_days: 2
  min_missing_share: 0.1

Only final days count (outside the DATA_IS_FINAL_DAYS window), so a late-arriving day does not raise the issue.

Expected Values​

Junk detection and type checks catch values that are broken. Expected values catch values that look fine but are wrong: a value of 1,000,000 on purchase, a transaction_id in the wrong format, or a currency your shop does not sell in. Wrong values like these flow into revenue and attribution reports without an error.

Write one rule per parameter. A rule needs param_name and at least one check:

expected_values:
  rules:
    - param_name: value
      event_name: purchase   # optional: only this event
      min: 0
      max: 20000
    - param_name: transaction_id
      event_name: purchase
      regex: '^[0-9]{12}$'
    - param_name: currency
      allowed: [EUR, GBP, CHF]
      rate_threshold: 0      # optional: any wrong currency raises the issue
KeyRequiredA value breaks the rule when
param_nameYes- (the parameter the rule covers)
regexOne of the four checksIt does not match. Uses REGEXP_CONTAINS, so anchor the pattern (^...$) for a full match
allowedOne of the four checksIt is not in the list (case-sensitive)
min / maxOne of the four checksIt is not a number, or it is outside the bounds (inclusive)
event_nameNoLimits the rule to one event; all events when left out
param_sourceNoevent_params_array, user_property_array or items_array; all sources when left out
rate_thresholdNo- (overrides expected_values.rate_threshold for this rule; a number from 0 to 1)
min_occurrencesNo- (overrides expected_values.min_occurrences for this rule; a whole number)

How the checks work:

  • Every value is checked, not only the stored samples, so a rare wrong value is still counted. The count lands in unexpected_occurrence_count per parameter, event and day.
  • A value must pass every rule that covers it. Several rules for the same parameter and event combine.
  • Junk is counted once. A junk placeholder (such as undefined) counts as junk only, not also as unexpected.
  • NULL means not checked. unexpected_occurrence_count is NULL where no rule covers the parameter, and 0 where it was checked and every value passed.
  • The issue needs a real share. A row gets the unexpected_values issue when at least rate_threshold (default 0.01) of its occurrences break a rule, with at least min_occurrences (default 20) occurrences that day. Set both per rule where the tolerance differs: rate_threshold: 0 raises the issue for any wrong value.
  • Overlapping rules: the lowest threshold wins. Where several rules cover the same parameter and event, the row uses the lowest rate_threshold and the lowest min_occurrences of those rules, so the most sensitive rule decides. The issues table shows the threshold that applied in evidence_threshold.
  • Rules are checked at compile time. A rule with no check, an unknown key, a bound that is not a number, a rate_threshold outside 0 to 1 or a fractional min_occurrences (also at block level), min greater than max, an allowed entry that is neither a string nor a whole number, or a regex that BigQuery cannot run (lookarounds, backreferences, a line break) stops compilation with an error that names the rule.
tip

Calibrate a rule on your own data before you turn on its assertion: check the range, format or value list of the last few weeks, then set the bounds with some headroom. A rule that is too tight raises an issue every day.

Good to know:

  • Item parameters with the same name. Without param_source, a rule also covers an item parameter of the same name - for example currency on items as well as on the event. Set param_source to limit it.
  • Long numeric IDs. min and max compare as floating point (about 15 significant digits). Check long numeric IDs with regex instead.
  • Quote values that look like numbers. In allowed, write '007' rather than 007: YAML reads an unquoted 007 as the number 7. Decimal numbers are rejected for the same reason.
  • History. A rule applies from the next run. To apply it to past days, reprocess ga4_parameter_detection_report_daily.

PII Detection​

The PII detection feature scans your GA4 parameters for personally identifiable information - both in parameter names and in actual collected values. This helps you identify privacy risks before they become compliance issues.

PII detection is on by default. To turn it off, or to mask detected values, set the keys under pii_detection in your custom file:

pii_detection:
  enabled: false             # only if you want to turn PII detection off
  mask_pii_in_samples: true  # replace detected PII in sample values

How it works​

PII detection operates on three levels:

  1. Parameter name detection: Checks the names of non-standard parameters against 46 known PII names (exact match, case-insensitive, e.g. email, phone_number, ssn, credit_card) and 13 suspected name patterns. The patterns are anchored on a name boundary: user_email, phone_number, lastname, date_of_birth and street_address match; is_mobile, email_opt_in, license_type and birth_year do not. Hits get the type parameter_name_indicates_pii.

  2. URL query keys: For page_location and page_referrer, the decoded query and fragment keys are checked against the same name rules. A URL like https://www.example.com/signup?email_address=... gets the type url_query_param_name_indicates_pii. A key only counts when its value has at least url_query_key_min_value_length characters (default 3), so short values such as ?ssn=en are ignored.

  3. Value pattern detection: Scans values with 17 configurable regex patterns with optional SQL validation. Values are percent-decoded twice before the scan, so jane.doe%40example.com and double-encoded %2540 are caught. For page_location and page_referrer the patterns run on the decoded query and fragment values, and the email pattern also runs on the decoded URL path (e.g. /account/jane.doe@example.com/). Other standard parameters are never flagged. Credit card detection uses both a regex pattern and a Luhn checksum validation to reduce false positives.

Issue Model​

The module turns its findings into issues with a type and a severity. Each issue is tracked per parameter, source and event (PII per parameter), so you can see when it started, whether it is still active, and how to fix it.

Where issues show up​

  • report_daily.issue_types: raw detections per day and event (pii, type_mismatch, junk_values, unexpected_values, type_difference, multiple_data_types). Not suppression-aware.
  • aggregated: unsuppressed issue types per parameter and event (plus missing_days), the highest issue_severity, and the suppression columns.
  • issues: one row per issue with first/last detection date, is_active, evidence and a description with the suggested fix. Start here for an audit.

An issue is active while it was last detected within issues.active_within_days (default 3) of the latest report day. After that it gets a resolved_date.

Suppressions​

Use suppressions for known, accepted findings. A suppressed issue stays in report_daily.issue_types as raw evidence, but is marked is_suppressed in aggregated and issues and skipped by the assertions.

suppressions:
  - param_name: search_term
    issue_types: [pii]
    reason: "Search box echoes typed emails; cleaned in GTM, ticket ABC-123"
    param_source: event_params_array
    event_name: search
    expires_on: '2027-01-31'
KeyRequiredDescription
param_nameYesParameter the suppression applies to
issue_typesYesNon-empty list of issue types (see Issue types)
reasonYesWhy the finding is accepted; shown as suppression_reason
param_sourceNoevent_params_array, user_property_array or items_array; any source when left out
event_nameNoEvent to limit the suppression to; any event when left out
property_idNoGA4 property to limit the suppression to; any property when left out
expires_onNoLast day the suppression applies (YYYY-MM-DD)

The list is validated at compile time: a missing required key, an unknown issue type or an invalid expires_on stops compilation with an error that names the entry.

Assertions​

Five opt-in assertions turn issues into alerts. A failing assertion ends the workflow run as failed, so the email alerts for Dataform errors report it. The alert message contains parameter names, events, issue types and counts only - never sample values.

AssertionFails whenWindow
piiA parameter carries potential PII on any day of the windowlookback_days: 3, provisional days included
junk_valuesA parameter carries junk values on at least min_consecutive_days: 2 consecutive dayslookback_days: 7, final days only
unexpected_valuesA parameter carries values breaking an expected-values rule on at least min_consecutive_days: 2 consecutive dayslookback_days: 7, final days only
type_mismatchA configured type loses occurrences on any daylookback_days: 7, final days only
missing_daysA parameter present on at least min_prior_presence: 0.5 of the event's days, and on at least min_prior_present_days: 2 days, in the 28 days before the window is absent on at least min_missing_days: 2 dayslookback_days: 7, final days only; needs min_baseline_days: 7 days of data in the 28-day baseline

Suppressed issues never fail an assertion. With alert_on: new_only (the default), a finding only fails the run when the same issue was absent in the 28 days before the window - one alert per new problem. The issues table keeps showing it until you fix or suppress it. Set alert_on: always to fail every run while the issue is in the window.

assertions:
  pii:
    enabled: true
  type_mismatch:
    enabled: true
    alert_on: always

The missing_days baseline reads report_daily, so rows written before an update count. Two floors keep it quiet on thin history: a parameter seen on a single day never counts as "used to carry" (min_prior_present_days), and nothing is judged until the property has min_baseline_days days of detection data in the baseline - for example the first week after a new install.

Assertions only run when the module itself is enabled. The assertion tables are written to your quality dataset.

Discovered and Configured-but-Absent Parameters​

Two findings come from param_status rather than an issue type.

Discovered parameters​

Detection: param_status = 'discovered'

Parameters exist in your GA4 data but aren't configured in your config.js file. Assess their analytical value and decide whether to add them to your configuration, exclude them via the exclude_params setting, or possibly even modify your GA4 tracking to stop collecting them.

Resolution Options:

  • Add to CUSTOM_EVENT_PARAMS_ARRAY, CUSTOM_USER_PROPERTIES_ARRAY, or CUSTOM_ITEM_PARAMS_ARRAY
  • Use ga4_parameter_detection_config_suggestions view for ready-to-copy configuration code
  • Add to exclude_params list if uninteresting
  • Stop collecting them if they are not needed

Configured but absent parameters​

Detection: param_status = 'configured_absent'

Parameters are configured but don't appear in your actual GA4 data. The configured date range will greatly affect this flag since some parameters might not be recently collected, but could be relevant historically.

Resolution Options:

  • Verify GA4 implementation is sending the parameter
  • Remove unused parameter from configuration
  • Check if parameter was recently added and hasn't appeared yet

Upgrading from Earlier Versions​

To v2.2.18​

No rebuild is needed. The new unexpected_occurrence_count column is added to report_daily on the first run, and rules apply from that run.

If your report_daily history predates v2.2.17, reprocess it in place. Rows written before v2.2.17 have no host counts and no issue_types. Until they are filled, the junk_values, type_mismatch and pii assertions report issues that already existed as new for about a week. Reprocess the full history with REPROCESS_START_DATE / REPROCESS_END_DATE on ga4_parameter_detection_report_daily, in batches for long ranges.

warning

Do not use a full rebuild for this. A full rebuild recreates report_daily from max_lookback_days / start_date only and drops the older history. The missing_days baseline and your trend reports need that history.

To v2.2.17​

The update to v2.2.17 needs no rebuild. What to know:

  1. New columns are added automatically. On the first incremental run after the update, report_daily gets the 12 new columns in one ALTER TABLE. Existing rows are kept, with NULL in the new columns.
  2. Fill history by reprocessing. Rows built before v2.2.17 have no issue, coverage, junk or type-loss data, so aggregated and issues only evaluate days built with the new version. To fill a past range, reprocess it with REPROCESS_START_DATE and REPROCESS_END_DATE and the tag module_ga4_parameter_detection. Prefer reprocessing over a full rebuild: a full rebuild only covers the max_lookback_days / start_date range.
  3. PII detection stays as you set it. New installs have PII detection on. Older custom configs contain enabled: false under pii_detection, which still wins. Delete that line to use the new default, or keep it to stay opted out. Until then, the issues table shows a config_outdated row for pii_detection.enabled.
  4. Remove superseded name patterns. Older custom configs list the previous loose suspected_pii_param_patterns (such as .*mobile.*). Because lists are appended, they still over-match names like is_mobile. The issues table names them in a config_outdated row - delete those lines.
  5. Legacy columns are deprecated. has_potential_issue and issue_description (and missing_dates in aggregated) keep their previous logic so existing dashboards do not change. Move to param_status, issue_types and the issues table.

Some values change meaning or order with this version:

  • aggregated.unique_values_count is now an approximate distinct count instead of the number of stored samples.
  • aggregated.sample_values is ordered by occurrences instead of alphabetically.
  • aggregated.days_with_pii_detected counts days, so numbers can be smaller.
  • aggregated now includes configured parameters that were never found.
  • PII flags change: more URL findings (decoding, query keys, path emails), fewer name false positives.
  • Parameters listed several times in config.js (for example with two types) no longer produce duplicate rows.

AI Agent Skill​

The ga4df-parameter-audit agent skill lets an AI coding assistant run the audit for you. It reads the issues, aggregated and config_suggestions tables, reports findings from critical to info with evidence and a fix, and - after you confirm - applies config additions, type fixes and suppressions, and deletes config_outdated lines.
